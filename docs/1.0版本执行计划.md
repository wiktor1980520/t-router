# TRouter 1.0 版本执行计划

## 1. 文档目标

本计划用于将 TRouter 从“可演示、可内测、可小规模试商用”的阶段，推进到“可稳定收费、可持续运营、可进行正式对外推广”的 1.0 阶段。

本计划强调三件事：

- 能卖：支付、计费、套餐、定价策略可用
- 能稳：路由、监控、回退、日志、告警可用
- 能管：后台、运营、风控、审计、配置可用

---

## 2. 1.0 目标定义

### 2.1 产品目标

TRouter 1.0 应成为一个面向开发者与中小团队的多模型 AI API 网关平台，具备：

- 统一 OpenAI 兼容接入
- 主流模型稳定支持
- 可配置的多供应商路由
- 完整的账户、计费、账单、支付体系
- 基础运营与增长能力

### 2.2 版本验收标准

#### 产品层

- 支持 OpenAI-compatible、Claude、Gemini、Kimi、GLM
- 注册、登录、邀请码、API Key、充值、消费、账单闭环完整
- 后台可管理模型、供应商、路由、配置、邀请码

#### 技术层

- 请求失败可定位
- 供应商故障可回退
- 关键链路具备 request_id
- 支持基础限流与风控

#### 商业层

- 可以正常充值/入账
- 可以稳定扣费
- 可以形成基础利润统计

---

## 3. 版本里程碑拆解

### 里程碑 M1：商业闭环可用

目标：让平台具备“真实收费”的能力。

#### 需要完成

- 支付流程正式化
- 充值订单与回调幂等
- 后台人工补单/确认机制
- 账单记录与交易状态统一
- 新用户赠送和邀请码逻辑稳定化

#### 验收结果

- 用户可完成一次可追踪的充值
- 后台可确认到账与补单
- 账单、交易、余额三者能对齐

---

### 里程碑 M2：路由与稳定性可运营

目标：让平台具备“稳定对外服务”的能力。

#### 需要完成

- 路由策略增强
- 健康检查规则优化
- 失败熔断与恢复
- request_id 全链路暴露
- 后台展示供应商健康数据

#### 验收结果

- 某上游失败时可自动回退
- 管理员可看到失败来源、成功率和延迟变化

---

### 里程碑 M3：安全与风控可上线

目标：让平台具备“正式公开运营”的最低安全基线。

#### 需要完成

- 强制 JWT Secret 配置
- API Key 哈希化存储
- 去除默认管理员固定密码方案
- 基础限流（用户级 / API Key 级）
- 异常请求与恶意调用识别

#### 验收结果

- 敏感配置不再依赖默认值
- API Key 不以明文方式存库
- 高频刷接口行为可以被限制

---

### 里程碑 M4：运营与增长能力可执行

目标：让平台不仅能运行，还能增长。

#### 需要完成

- 用户增长看板
- 模型消费排行
- 成本与利润分析
- 注册转化与充值转化统计
- 邀请码来源分析

#### 验收结果

- 运营可以基于数据做活动
- 可以判断哪些模型该推、哪些用户值得激活

---

## 4. 分阶段执行计划

## 第一阶段：第 1-2 周

### 核心目标

完成“支付 + 账务 + 安全底线”的第一轮补齐。

### 任务清单

- 梳理充值订单状态流转
- 完成支付创建、回调、补单统一逻辑
- 对交易状态做标准化
- 移除默认管理员密码依赖
- 强制配置 JWT Secret
- 检查所有涉及余额更新的幂等问题

### 输出结果

- 可上线的充值闭环
- 可回溯的账务逻辑
- 安全底线不再依赖默认值

---

## 第二阶段：第 3-4 周

### 核心目标

把路由器从“能用”提升到“稳定可运营”。

### 任务清单

- 补供应商错误分类
- 记录失败率、延迟、回退次数
- 实现简单熔断
- 增加恢复策略
- 后台增加供应商健康可视化

### 输出结果

- 路由系统具备稳定性管理能力
- 可快速定位模型失败原因

---

## 第三阶段：第 5-6 周

### 核心目标

完成限流、风控、密钥安全改造。

### 任务清单

- API Key 哈希化存储
- API Key 校验逻辑升级
- 加入用户/API Key 级限流
- 增加消费阈值与异常调用检测
- 梳理管理操作审计

### 输出结果

- 安全性达到可公开运营要求
- 风控不再完全依赖人工判断

---

## 第四阶段：第 7-8 周

### 核心目标

完成运营看板和增长工具的第一版。

### 任务清单

- 用户增长指标
- 模型消费排行
- 充值与消费趋势图
- 邀请码来源统计
- 注册转化和充值转化统计

### 输出结果

- 运营可以基于后台数据制定活动
- 产品与模型策略可以数据驱动

---

## 第五阶段：第 9-12 周

### 核心目标

完成 1.0 封板前的优化、整理与对外发布准备。

### 任务清单

- 统一文档与接入说明
- 完善客户端接入模板
- 做版本发布说明
- 进行部署验证
- 梳理已知问题与升级计划

### 输出结果

- 可对外发布的 1.0 版本
- 面向用户的文档、后台、接入流程完整

---

## 5. 技术优先级建议

### P0

- 支付闭环
- 安全底座
- 限流风控
- 路由稳定性

### P1

- 运营看板
- 套餐能力
- 客户端生态模板

### P2

- 团队/组织
- 企业版功能
- 私有化能力

---

## 6. 资源建议

### 如果是小团队

建议按以下角色分工：

- 后端：支付、路由、Provider、安全、账务
- 前端：后台、看板、配置、接入体验
- 产品/运营：套餐、活动、文档、转化策略

### 如果只有 1-2 人

建议优先顺序：

1. 支付
2. 安全
3. 路由稳定性
4. 看板
5. 包月卡

---

## 7. 1.0 发布前检查清单

- 是否可稳定注册、登录、生成 API Key
- 是否可完成充值、到账、扣费、审计
- 是否可配置模型、供应商、路由
- 是否可追踪失败请求
- 是否可处理单供应商故障
- 是否完成默认安全项整改
- 是否具备基础限流
- 是否有最少一套对外接入文档
- 是否有最少一套运营后台数据看板

---

## 8. 最终建议

TRouter 1.0 不是“功能最多的版本”，而应该是“最能形成稳定商业闭环的版本”。

因此执行策略要坚持：

- 少做分散功能
- 多做核心闭环
- 优先补齐支付、安全、路由、运营数据

只要这四块做扎实，TRouter 就能从一个技术项目，进入真正的产品化阶段。
